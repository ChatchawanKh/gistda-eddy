HMAC-SHA256 ของ header.payload ด้วย JWT_ACCESS_SECRET ถ้ามีใครแก้ payload แม้ตัวเดียว ลายเซ็นจะไม่ตรง แล้ว jwt.verify จะปฏิเสธ

payload ไม่ได้เข้ารหัส ใครก็ decode อ่านได้ (base64url) ลายเซ็นมีไว้กันการแก้ไขเท่านั้น ห้ามใส่ข้อมูลลับลงใน payload

การป้องกัน secret อ่อน

config/validateEnv.js รันตอน start server ถ้าไม่ผ่านจะ process.exit(1) ทันที

  • ต้องตั้ง JWT_ACCESS_SECRET และ JWT_REFRESH_SECRET ทั้งคู่ ยาวอย่างน้อย 32 ตัวอักษร
  • ห้ามมีคำแบบค่าตัวอย่าง (change, replace, secret, example, your_)
  • สองตัวต้องไม่ซ้ำกัน ถ้าซ้ำ คนที่มี refresh token จะเอาไปใช้แทน access token ได้

เหตุผล: ถ้า secret ว่างหรือเดาได้ ใครก็ปลอม token ที่มี "role": "admin" ได้เอง

4การป้องกัน route ด้วย middleware

ทุก request ที่ต้อง login ผ่านด่านตามลำดับนี้ ด่านไหนไม่ผ่านจะตอบกลับทันทีโดยไม่ถึง controller

RequestAuthorization: Bearer <token>
↓

  • 401ไม่มี header Bearer
  • 401หมดอายุ → code: "TOKEN_EXPIRED" (frontend จะ refresh)
  • 403ลายเซ็นผิด / ถูกแก้ไข
  • ผ่านreq.user = { user_id, email, role } ไม่ query DB
↓

  • 401ไม่มี req.user (ลืมใส่ verifyToken ก่อน)
  • 403req.user.role ไม่อยู่ในรายการที่อนุญาต
↓

// routes/user.routes.js : ทุก route ในไฟล์ต้องเป็น admin

8ข้อสังเกตจากโค้ดปัจจุบัน

จุดที่โค้ดกับเอกสารไม่ตรงกัน หรือควรรู้ไว้ ข้อ 1 แก้แล้ว ข้อ 2–7 บันทึกไว้ ยังไม่ได้แก้โค้ด

1 · Request ที่เป็นตัวสั่ง refresh ค้าง แล้วถูกยิงซ้ำทีหลังแก้แล้วเดิมเป็นบั๊ก

ใน src/api/axiosClient.js เดิม request แรกที่เจอ TOKEN_EXPIRED จะ refresh สำเร็จ แล้วเรียก onRefreshed() ซึ่งปล่อยและล้างคิวไปแล้ว จากนั้นตัวมันเองค่อยเข้าคิว จึงไม่มีใครเรียกมันต่อ

ผลกระทบ (ยืนยันด้วยการรันโค้ดจริงกับ server จำลอง):

  • request นั้นค้างจนกว่าจะมี token หมดอายุรอบถัดไป ถ้าไม่มีก็ค้างตลอด หน้าที่มี spinner (เช่นโหลดรายชื่อผู้ใช้) จะหมุนค้าง ส่วนปุ่มที่ไม่มี loading (เช่นเปลี่ยนสิทธิ์) จะกดแล้วเงียบ
  • request ที่ค้างไม่ได้หายไป แต่ถูกยิงไป server ใหม่ตอน refresh รอบถัดไป ถ้าเป็นการแก้ข้อมูลจะทับค่าที่ใหม่กว่าได้ เช่น ตั้งสิทธิ์เป็น admin (ค้าง) → กดซ้ำสำเร็จ → เปลี่ยนกลับเป็น user → รอบ refresh ถัดไป role กลับเป็น admin เอง (server ได้รับ admin → user → admin)

การแก้: หลัง refresh สำเร็จ request ตัวที่สั่ง refresh ยิงตัวเองซ้ำทันทีด้วย token ใหม่ ไม่เข้าคิว

onRefreshed(data.accessToken);
originalRequest.headers.Authorization = `Bearer ${data.accessToken}`;
return axiosClient(originalRequest);

ใช้ return โดยไม่ await เพื่อให้ error ของ request ที่ยิงซ้ำ reject ตามปกติ ไม่ตกไปที่ catch ที่เด้งไปหน้า login

2 · Access token เก็บใน localStorageความปลอดภัย

README ข้อ 5 บอกว่าเก็บใน memory/React state แต่ AuthContext.jsx และ axiosClient.js ใช้ localStorage ถ้าเว็บโดน XSS สคริปต์ของคนร้ายจะอ่าน token ได้ ส่วน refresh token ยังปลอดภัยเพราะอยู่ใน httpOnly cookie

3 · อายุ refresh token กำหนดไว้ 3 ที่ค่าตั้งไม่สอดคล้อง

JWT ใช้ REMEMBER_ME_EXPIRES_IN / SESSION_EXPIRES_IN แต่ expires_at ใน DB (auth.controller.js บรรทัด 126) และ cookie maxAge (บรรทัด 142) hardcode เป็น 30/1 วัน ถ้าแก้ค่าใน .env สามค่านี้จะไม่ตรงกัน

ส่วน JWT_REFRESH_EXPIRES_IN=7d ใน .env.example และ README แทบไม่ได้ใช้ เพราะ login ส่งอายุเข้าไปเองทุกครั้ง

4 · ไม่มี refresh token rotationความปลอดภัย

/refresh คืนแค่ access token ใหม่ refresh token ตัวเดิมใช้ซ้ำได้จนหมดอายุ (สูงสุด 30 วัน) ถ้า cookie หลุด คนร้ายใช้ได้จนกว่าผู้ใช้จะ logout หรือเปลี่ยนรหัส

5 · สิทธิ์ใน token ไม่อัปเดตทันทีข้อแลกเปลี่ยน

verifyToken ไม่ query DB ถ้า admin ระงับบัญชีหรือลด role ผู้ใช้ยังใช้ access token เดิมได้อีกไม่เกิน 15 นาที นอกจากนี้ /refresh เช็ค is_active แต่ไม่เช็ค is_approved

6 · Rate limit ใช้ memory storeDeploy

บน Vercel (serverless) ตัวนับแยกกันต่อ instance และหายเมื่อ cold start จึงกัน brute-force ได้ไม่เต็มที่ ควรใช้ store ภายนอก เช่น Redis/Upstash

7 · ตาราง refresh_tokens ไม่มีการลบแถวเก่าดูแลระบบ

login ทุกครั้งเพิ่ม 1 แถว แถวที่หมดอายุหรือ revoke แล้วไม่ถูกลบ ควรตั้ง job ลบเป็นระยะ

DELETE FROM refresh_tokens WHERE expires_at < NOW() OR revoked;
